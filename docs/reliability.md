# 网络与提交可靠性合同

用户动作可以重试，业务事实不能重复；网络状态可以未知，系统不能猜测；通知可以延迟，使用权不能漂移。

## 成功、未知与回执

每个写动作在发出前生成并保存 request key、actor、操作和原 DTO。服务器在协调锁内核实当前权限/期限，副作用、接收时间、收据与通知事件同事务提交。HTTP 响应和 toast 都不是新的权利来源；只有成功提交的事实才成立。

断网/超时显示“结果确认中”，保留草稿和原键。GET receipt 返回 COMMITTED 时读回详情；404 仅表示当前没读到已提交回执，原请求仍可能在途，不能换键/改内容生成新业务。503 是未能确认，不能解释成业务不存在。重试使用同一 actor/key/operation/body，恢复登录也不得以新 actor 重放旧动作。

重试有次数和时间预算，结束预算后保留确认入口与原键，不无限阻塞整页。读成功只清理该读取自己的错误，未知写必须通过原收据/详情确认。响应丢失后原键重放返回原结果，记录当前状态则通过详情查询；历史收据不假装是最新状态。

## 截止与延迟

客户端发出时刻、网关到达时刻和手机时间均不能争取资格。接收时间指事务取得协调锁、通过当时期限检查而接受该动作的服务器时间，并且该事务必须成功提交。不能在客户端预占名额。回执记录这个时间和版本，绝不把请求最初到达但仍在排队的时间倒填成接收时间。

响应包到达时间不撤销已经成立的事实。过截止的重复请求若有成功收据，返回同一历史收据；没有成功收据时按当前时间裁决，不补造截止前的事实。MySQL不提供给此应用精确的物理刷盘时刻，本合同不把采集的接收时间伪称磁盘提交时间；锁序、状态、期限和收据共同建立业务接受的先后顺序。

长期抽签遵守冻结快照、唯一来源和 [结果时限](contracts/allocation.md)，重启复算相同输入，不重抽；到结果截止没有合法结果则明确失败和替代路径。

## 通知与恢复

业务写与 outbox 事件在同一事务；站内 inbox 的去重投影随后独立提交。投递失败不会删除已经提交的使用权/候补。公开结果页始终是权威入口，通知为提醒。CREATED/PENDING、INBOX可读、READ 是不同状态；没有配置的微信/短信/邮件渠道不声称送达。

M4 增加管理端待投递年龄、失败尝试及恢复待办；断网/依赖不可用时保持明确故障，不把空数据展示成无申请。长期批次需全体申请人结果事件，包含无匹配和故障，不仅给中签者发通知。

## 证据要求

真实 HTTP 故障中继在上游已提交后丢弃响应，原键重放和详情读回必须只有一次效果；确认截止之后重放已成立确认不得释放。另构造尚在途时 receipt 404，再恢复提交，证明404不是事务未发生证明。通知写失败注入验证事务回滚（这是受控异常，不冒充物理 MySQL 断电），恢复同键只有一个副作用和事件。M6另验证真实进程恢复/依赖故障，不把本阶段测试升级成全生产可靠性。
