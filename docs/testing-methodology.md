# 代表性失败机制测试与独立产品复验

参考方法 v0.1 · 整理自期序本轮 M7/M8 · 2026-10-03

**这是参考方法，不是教条，也不是三个其他仓库的验收报告。** M7/M8 是期序的阶段编号；别的工程可以采用自己的编号、工具和门禁。复用的是提问方式、证据纪律和停止条件，不是期序的业务规则、测试数量、数据库结构或完成结论。目标项目的现行合同与用户授权优先；发现规则本身有问题时，先明确修订最小边界，保留旧规则下的原失败。

用户已授权在期序完成之后，依次将此方法用于暗室藏书、素简记和 MiniSpringBoot。先完成期序，不并行扩张三个工程。后续开始时必须重新读取目标仓库的当前源码、施工规则、公开基线与环境；本页不授予尚未执行的测试任何 PASS。

## 1. 先问项目究竟承诺什么

先画出事实链，再找可能击穿承诺的反例。事实链来自该项目的业务，而非套用“登录、CRUD、压力测试”模板。

```text
声明与规则 → 谁拥有事实 → 状态转换 → 持久提交
          → 页面/消息投影 → 失败恢复 → 公开交付
```

例如，期序关心空间使用权；藏书关心库存与流通；素简记关心订单、支付、库存和跨服务收敛；MiniSpringBoot 还必须区分框架内核与 demo 应用。各自先回答：

- 哪些事实只能由哪个主体、模块或服务改变？查询结果何时只是观察，何时能授权写入？
- 哪些状态必须唯一、原子、不可倒退或可恢复？两个各自合法的流程组合后能否非法？
- 谁承担时间、身份、版本和结果未知的裁决？外部系统不可用时还能做什么？
- 哪些后果最严重：越权、丢事实、重复效果、错误库存/权利、泄露、伪完成，还是短暂不可用？
- 当前究竟支持单实例、多实例、真实中间件或特定设备中的哪些范围？

把答案变成少量可直接验证的不变量。不要让测试数量代替它们，也不要凭已有绿灯假定当前版本成立。

## 2. 每轮先固定入口和预算

执行前记录以下入口；不明确时先补合同和资源归属，再动手。

| 项目 | 必须明确的内容 |
| --- | --- |
| 坐标 | 仓库、分支、exact SHA、工作树变更、构建来源、依赖/迁移版本 |
| 声明 | 本轮要证明什么、保护什么、不做什么、哪些仍未证明 |
| 范围 | 主要机制、代表性反例、必要的高风险组合、受影响正常链路 |
| 判定 | 预期不变量、独立事实判定方式、必需原始证据、停止条件 |
| 资源 | 专用库/账号、owned 进程与句柄、端口、已有共享服务、清理入口 |
| 预算 | 宿主内存/连接/时间预算、故障持续窗口、资源不足时的中止与留证方式 |

已有用户修改和原失败候选均保留，修复使用独立分支与单一目的提交。数据库、浏览器和容量验收按宿主资源串行，不因多个代理而争用同一夹具。停止已有进程前核对实际身份，不能按端口或进程名推测归属。只测试授权工程及隔离依赖，不扫描无授权外部系统。

## 3. 错题来源先迁移，再验证

输入可以来自用户反例、GitHub issue/修复 PR、官方文档、其他工程事故和独立审阅。保存原链接、版本或提交、触发前提与讨论中的证据层级。

对每条来源依次判断：

1. 目标项目是否拥有同样的机制及可达路径？没有就登记不适用及理由。
2. 上游发生的是产品问题、协议限制、环境故障，还是测试前提错误？
3. 将其翻译成目标项目自己的最小反例，给出自己的预期和事实判定。
4. 再问一个有价值的邻近问题，例如锁等待后权限是否变了、提交后响应是否丢了；不无限生成排列。

别人的修复不是本项目的证明。没有运行上游测试，就不能写“已复现上游”；没有目标项目实际证据，就只能写风险假设或静态推导。原始来源和迁移记录可放进错题本，实际失败另有身份。

## 4. 覆盖单位是机制，不是所有切点

以下是选择入口的参考地图。按业务删改、合并或新增；无对应能力的项可明确不适用，不能为了填满表格人为造功能。

| 机制 | 代表性提问 |
| --- | --- |
| 时间与版本 | 截止前发出、锁后才处理；修订与冻结竞争；任务迟到会否延长资格？ |
| 并发与复合状态 | 两个最终写入竞争；两个局部合法流程会否重复占用、超卖或失去原事实？ |
| 幂等与 UNKNOWN | 同键重试、同键异正文、提交后丢响应；查不到能否被误解释为没有效果？ |
| 身份与权限 | A 切 B、旧凭据迟到、范围撤销、上游身份不可用；拒绝后有无业务副作用？ |
| 请求与页面生命周期 | 离开页面后旧响应/辅助请求继续；旧列表、照片或错误能否污染当前主体？ |
| 原子提交与恢复 | 事务中断、完整提交后进程停止、恢复旧库；外部世界是否仍向前？ |
| 依赖与有限等待 | 连接/锁/网络耗尽预算；降级是否猜测事实或放宽权限？ |
| 通知与查询投影 | 事实已提交但提醒失败；已送达是否冒充已读；分页/缓存是否伪装完整？ |
| 公平与进展 | 固定扫描窗口导致饥饿；可用资源被算法闲置；重试/租约是否永远卡住？ |
| 数据与协议 | 未知与 false 混同、重复字段、边界值、解析歧义、私有信息与公开投影混同？ |
| 启停与交付 | readiness/drain、冷启动依赖、demo 与真实模式、公开文档和实际入口是否漂移？ |

优先切身份、权限、时间、事务、恢复、外部依赖与页面所有权边界。通常区分请求未到、提交中断、提交后丢响应；它们有不同合法结果，不能用一次 timeout 覆盖三种语义。

关键单故障给代表性反例，高风险交叉只选择有新增价值的少量组合。算法的小规模独立穷举可以有效，但不能扩展为“所有业务节点、所有路由、所有故障全排列”。切点能无限细分，测试必须有有限退出条件。

## 5. 证据要直接碰到不变量

先在正常链路证明夹具有效，再施加一个明确故障，观察拒绝或恢复；必要时保留未修候选作为负控制。故障必须确实到达目标边界，不能只看注入开关已经打开。

| 证据层 | 能支持什么 | 不能自动支持什么 |
| --- | --- | --- |
| 静态源码推导 | 存在路径、缺少守卫、潜在影响 | 已运行复现、所有调度必失败 |
| 单元/受控模型 | 时间、状态与协议的明确语义 | 真实数据库锁、物理断网、设备行为 |
| 实际框架组件/客户端 | 真实源码与运行时下的状态归属、路由续体 | 浏览器政策、微信真机、全部页面 |
| HTTP + 真实数据库 | 权限、事务、唯一效果、最终行及持久回执 | 生产容量、其他部署拓扑、用户已收到通知 |
| 隔离进程/协议故障 | 已明确触发的重启、回应丢失或依赖失败 | 真掉电、整机回退、全部指令点 kill |
| 实际页面操作 | 本次视口/身份/链路的可达性与页面结果 | 仅凭截图证明完整操作顺序、物理设备通过 |
| 独立报告/Core/CI | 各自合同内的复核、裁决或门禁事实 | 零缺陷、超出证据边界的发布资格 |

期望值尽量独立：小算法用独立穷举或参考模型；事务读原始数据库终态、回执与关联记录；权限从当前身份/范围事实推导；通知逐项核对业务结果与持久记录；页面核对主体、路由、请求来源及服务端事实。不要调用被测 Service 的同一计算路径生成“正确答案”。

受控 Clock 与真实锁可检验截止语义，但不是物理时钟跳变；缓存或 mock 可以检验某一分支，但不能替代该项目承诺的真实依赖。截图、录屏、请求、DOM、视口、源坐标和操作序列按需要绑定。公开材料只用明确演示数据并去除票据、密钥和私有身份，保留摘要；私有原件另存。

## 6. 每个发现只保留一条可追踪记录

```text
编号 / 所属机制 / 风险
目标 SHA、合同版本、环境与证据层级
正常前提 → 最小操作/调度 → 实际结果
预期不变量 / 独立判定方式
首次失败原件及摘要
分类、影响范围、处置依据
最小修复 SHA / 原条件复验身份
必要邻近回归 / 剩余边界
跟进人 / 再进入条件与入口
```

先保存首败再修。缩减失败序列以定位机制，原长 trace 仍保留。源码、前提或观察合同变更时产生新身份，不覆盖旧输出，也不事后修改旧 Plan 让它变绿。

分类至少区分：真实产品缺陷、正确拒绝、测试/夹具错误、采集器错误、执行环境阻断、已修的历史问题、不适用和未证明。工具启动失败不算产品缺陷；正确拒绝不算功能坏了；恢复后的 PASS 也不能抹去首败。发现采集器误判时修它的最小观察边界，保留正确业务断言。

修复后先重放原条件，再验证受影响的正常/相邻链路。禁止更换幂等键、重抽随机值、清空关键事实或放宽权限来制造通过。重启和重试属于恢复操作：症状消失后仍要核对持久事实、归属和回执；静默错误不会因重启自动修复。

## 7. M7 与 M8 的职责分开

M7 用代表性反例建立机制地图和防线，完成必要修复、独立事实判定及未知账册。M8 从固定候选走真实产品，检查这些防线是否在具体实现中遗漏，以及用户能否理解状态、完成任务和安全恢复。

M8 至少安排两种独立视角：

- 测试者：从固定源码、业务合同和原始证据重新挑战关键声明，给最小复现或明确静态推导。
- 产品经理：先看实际页面证据，再检查信息、入口、角色、反馈、错误恢复、返回上下文和移动端办事能力。

审阅者可以读取原失败和证据，但不能继承施工者“已完成”的自评。只独立看了别人采集的截图，要写清未亲自操作；只运行了离线组件，要写清未跑浏览器/数据库。代理数量不产生资格。

同类机制在另一个页面漏网，照常登记、修复并回归，不自动否定此前限定见证。只有新机制、原证明被推翻或特殊高风险，才重开最小相关机制边界。前端精修可单列阶段；内容不准确不能被归成纯视觉而消失。

## 8. 何时停止，何时重新进入

达到以下条件可收束本轮：主要机制有代表性反例；关键不变量有直接证据；高风险交叉有必要的少量验证；范围内已观察到的核心缺陷已修复复验；其他发现有明确处置；剩余未知与公开声明一致且能追踪。

再遇一个反例，先判断它是否带来新机制、新事实所有者、新状态机冲突、原证明反证或显著更高风险。只是已知机制的相似排列时，停止扩张测试模型，按普通缺陷风险修复。停止扩张不允许忽略已经观察到的核心问题，也不能以“不再有任何 bug”作为退出目标。

每项 UNKNOWN / NOT_PROVEN 记录触发条件、可能影响、缺哪层证据、当前不能验证的原因、所需环境、具体重入入口及维护归属。没有测过、工具不支持和明确不适用分开记录。

本方法不估计“已消除 80%～95% 风险”，也不把测试数量换算成安全概率。未知问题可能来自低频组合，也可能来自未建模的机制；没有观测分布，不能声称它们几乎不发生或只需重启。后续通过日志/请求坐标、用户反馈、事实对账与最小复现吸收长尾：新发现 → 留证 → 分类 → 必要修复 → 有价值的回归见证。

## 9. 完成声明跟随当前证据

代码写完、执行结束、测试通过、合同范围内获得资格、公开状态生效是不同状态。固定候选的证据不能因内容相同而自动授予合并后的另一 SHA。

沿目标仓库既定门禁完成：本地限定验收 → PR 检查 → 受保护合入 → 新 exact-main 检查 → 必需的新安装/页面读回 → 独立对齐 → README/版本/Release。文档修订不冒充产品通过，页面展示数据不冒充真实后端验收；每条状态都要能定位到相应来源。

目标项目若使用 VeriTrail，先按其实际支持边界封存 Plan，再采集事实并由公开 Core 裁决，保留原 Bundle。它不替业务选择测试、不凭空提供数据库/多服务/真机能力，也不取代最终发布授权。是否接入、证明哪些范围，由目标仓库合同决定，不照搬期序采集器。

## 10. 期序本轮值得带走的教训

| 实际发现 | 可迁移的提问方式 |
| --- | --- |
| 前十个批次占据扫描窗口，第十一个无法进展 | 增大 LIMIT 只是延后同一反例；检查扫描是否真正有进展保证 |
| 冻结截止已过、公布截止未到，存储阶段仍阻止合法下一步 | 页面终态、资格投影和持久处理进度要分开；不能只测试两个期限都过了 |
| 候补 DTO 版本与申请版本混同 | 相邻对象版本不是一个并发控制坐标，拿真实返回值走端到端链路 |
| Bearer 登出清掉无关 Cookie；内部恢复/旧页面影响新主体 | 控制主体、会话代际与恢复归属；拒绝/清理也可能有跨主体副作用 |
| 旧页面主请求结束后继续发辅助请求，占用新页面 lane | 守卫不仅放在赋值处，还检查续体是否仍有权启动下一步 |
| 未知设施状态被写成 false；反馈编号和决定信息不完整 | 不猜事实；后端正确也要检查用户是否理解当前对象与合法决定依据 |
| 构建缓存、夹具、EOF 和采集文本判定各自造成失败 | 先分类、核对实际源码和产物；不把工具错误解释成产品修复 |

依据分别见[机制账册](m7-coverage-ledger.md)、[覆盖复核](coverage-review.md)、[M8 原始发现与处置](acceptance/m8.md)。它们保留历史 source 与原 evidence 身份；这些案例说明方法的价值，不证明别的仓库存在相同缺陷，也不升级期序尚未闭合的公开交付状态。

## 11. 三个目标仓库的适配起点

以下从各项目现有定位选出待核对的入口，**均为期序完成后的计划，尚未执行本轮攻击**。开始时重新绑定远端/本地当前 SHA、已有用户变更、工程合同与运行能力；不将旧 README 数字当 fresh 结果。若实际实现与下列描述不同，以实际事实修订入口。

| 项目 | 首先恢复的事实 | 值得优先攻击的机制 | 应避免照搬 |
| --- | --- | --- | --- |
| [暗室藏书](https://github.com/NoctilumeDev/DarkRoomLibrary) | 读者权限、库存、借还/续借/预约、采购物流入库、内容治理及可降级依赖的所有权 | 最后一本并发借阅；还书/续借/排队交叉；重复入库；旧权限；缓存/MQ失败与事实恢复；多角色页面及未知提交 | 期序的抽签、公平席位和空间状态机；Pages demo不能替代真实流通事务 |
| [素简记](https://github.com/NoctilumeDev/PlainJournal) | 单经营主体边界、订单/支付/库存等事实所有者、Outbox/补偿/对账、历史与当前前端基线 | 取消/支付/退款竞争；重复或乱序消息；旧worker/租约；超时未知；跨服务恢复与错误补偿；换号/结算页面 | 跨服务业务不能压成一个本地事务；不进入PlainJournalPro多商户范围，不把宿主容量中止填成PASS |
| [MiniSpringBoot](https://github.com/NoctilumeDev/MiniSpringBoot) | 框架内核与demo分轨，Bean/配置/AOP/HTTP/JDBC/启动关闭合同、依赖边界 | 部分启动与失败清理；就绪/排空；代理异常和事务边界；线程资源归还；解析歧义；重复关闭；demo真实数据库链路 | 不强加座位/电商业务；不因教学内核定位而降低demo已承诺的可用性，也不要求未声明的Spring完整兼容 |

三仓各自产生自己的范围合同、错题本、首败、最小修复和原条件复验记录。方法论在期序公开保存，测试结论和源码修复归各目标仓库；不能给三个仓库复制一张通用 PASS 表。

## 12. 开始下一仓库时的交接清单

1. 读本页并确认其参考性质；读取目标仓库实际规则、版本与未证明账册。
2. 恢复业务事实链和高价值不变量，给本轮适用/不适用的机制与停止线。
3. 先保存固定基线、资源归属和正常对照，再迁移公开错题并执行代表性攻击。
4. 首败留证、分类、最小修复、原条件复验；只补有新增价值的邻近验证。
5. 测试者与产品角色独立复核；明确亲操、看原件、模型或静态分析的层级。
